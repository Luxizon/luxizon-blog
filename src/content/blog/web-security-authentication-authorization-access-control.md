## 认证与授权解决不同的问题

**认证（Authentication）确认身份，授权（Authorization）判断某个主体是否有权对某项资源执行某个操作。**

以在线学习平台为例：

| 环节 | 要回答的问题 | 示例 |
| --- | --- | --- |
| 认证 | 当前访问者是谁？ | 验证登录凭据，确认访问者是学生甲 |
| 会话管理 | 后续请求对应哪个身份？ | 校验会话 Cookie，并找到对应的登录用户 |
| 授权 | 这个身份能执行本次操作吗？ | 判断学生甲能否查看某份成绩单 |

登录成功不意味着能访问所有已登录用户的数据。学生甲和学生乙都通过了认证，学生甲仍不应因此获得学生乙的成绩单。

授权也不只是在用户表中读取一个角色：它可能同时取决于资源归属、所属组织、操作类型和业务状态。公开文章可以允许匿名阅读，修改文章则需要额外权限。

PortSwigger 将认证、会话管理和访问控制分别讨论，有助于避免把“已经登录”误当成“有权访问”。参见其[认证专题](https://portswigger.net/web-security/authentication)与[访问控制专题](https://portswigger.net/web-security/access-control)。

## 垂直越权：跨越功能权限边界

垂直越权指用户访问了超出自身权限的功能。例如，普通学生调用本应仅供教务管理员使用的成绩导出接口。

假设普通学生的页面没有“导出全校成绩”按钮，但服务端存在以下接口：

```http
GET /api/admin/grades/export HTTP/1.1
Host: academy.example
Cookie: session=DEMO_STUDENT_SESSION
Accept: text/csv

```

这只是说明权限边界的请求示例。预期的安全行为是：服务端识别出学生身份后拒绝导出，且不返回成绩数据。如果接口只检查是否登录，随后就生成全部成绩，才构成这里假设的授权缺陷。

关键不在于用户是否把自己的角色字段改成了管理员。即使角色始终是普通学生，只要成功执行了管理员专属操作，也已经越过权限边界。

## 水平越权：跨越资源归属边界

水平越权常发生在权限级别相近的用户之间。例如，商城用户甲有权查看自己的订单，却能读取用户乙的私人订单。

假设订单 `4101` 属于甲，订单 `4102` 属于乙。下面两个请求使用同一个甲的会话，只改变资源编号：

```http
GET /api/orders/4101 HTTP/1.1
Host: shop.example
Cookie: session=DEMO_USER_A_SESSION

```

```http
GET /api/orders/4102 HTTP/1.1
Host: shop.example
Cookie: session=DEMO_USER_A_SESSION

```

只有在业务规则不允许甲查看乙的订单，而第二个请求仍泄露订单内容时，才能据此判断存在越权。**修改编号本身不是漏洞；缺失有效的对象级授权才是问题。**共享文档等场景还需要考虑明确授予的共享权限，不能仅凭所有者不同下结论。

通过用户可控标识直接访问对象、却没有正确检查权限，是不安全直接对象引用（IDOR）的典型情形。使用不可预测的 UUID 替代顺序编号可以提高猜测难度，但不能代替授权检查。[PortSwigger 的访问控制介绍](https://portswigger.net/web-security/access-control)进一步讨论了这些概念。

## 为什么权限校验必须在服务端进行

浏览器运行在访问者控制的设备上。隐藏按钮、禁用输入框和前端路由守卫可以改善操作体验，却不能阻止访问者绕过界面发送 HTTP 请求。

例如，前端提交下面的字段，并不会让它们自动成为可信事实：

```json
{
  "userId": "user-a",
  "role": "admin",
  "orderId": "4102"
}
```

服务端应从经过验证的会话或令牌中确定当前主体，再依据可信的权限数据判断请求，而不是相信请求体中的 `role`。如果使用带签名的令牌，也需要验证签名、有效期及适用范围；仅解码其内容不等于验证成功。

以“只能读取自己的订单”为业务规则，服务端处理可以概括为：

```text
主体 = 校验会话并获取当前用户
如果主体无效：拒绝请求

订单 = 查询满足以下两个条件的记录：
       id 等于请求中的订单编号
       owner_id 等于当前用户的可信用户编号

如果没有符合条件的订单：拒绝访问或按统一策略返回不存在
否则：仅返回允许公开给该用户的订单字段
```

这是简化的教学伪代码，不是完整生产实现。若业务允许客服、共享成员或组织管理员访问，需要显式加入相应规则；不能不加区分地套用所有者判断。

拒绝请求也必须发生在返回敏感内容或执行写操作之前。不能先修改数据库，再返回错误页面；也不能先把数据发到浏览器，再依靠前端把它隐藏。

## 防护应覆盖每次请求和每类操作

依据 [OWASP 授权防护指南](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)，可以用以下原则审视实现：

- **默认拒绝、最小权限**：没有明确允许规则时拒绝访问，只授予完成任务所需的权限。
- **逐请求校验**：页面、API、下载和导出接口都需要保护；多步骤流程不能只检查第一步。
- **检查主体、资源与操作的关系**：有权读取不代表有权修改或删除；还应考虑租户边界和业务状态。
- **集中维护规则**：复用授权逻辑，避免不同接口各自实现后出现遗漏；集中逻辑仍需接入每个受保护入口。
- **覆盖拒绝场景**：不仅测试合法用户能访问，也测试匿名用户、其他用户、低权限角色和其他租户应被拒绝。

针对前面的订单场景，可以先写一张预期权限表，再设计测试：

| 请求主体 | 目标资源 | 操作 | 在该假设业务下的预期 |
| --- | --- | --- | --- |
| 用户甲 | 甲的订单 | 查看 | 允许 |
| 用户甲 | 乙的订单 | 查看 | 拒绝 |
| 未登录访问者 | 甲的订单 | 查看 | 拒绝 |
| 普通学生 | 全校成绩 | 导出 | 拒绝 |

这些是待验证的预期结果，不是已经获得的实验结果。验证时还应检查响应正文与实际业务副作用，不能仅凭页面提示判断权限控制是否生效。

## 如何利用 Web Security Academy 继续学习

PortSwigger Web Security Academy 的[认证专题](https://portswigger.net/web-security/authentication)和[访问控制专题](https://portswigger.net/web-security/access-control)把概念说明与专门设计的实验环境结合起来。它的学习价值在于：可以把“谁、对什么、做什么”的权限问题对应到具体请求，而不只记住漏洞名称。

后续可以按以下顺序学习；这是一份建议，不是已完成清单：

1. 先阅读认证、会话与访问控制的概念，写清它们各自负责什么。
2. 选择相关入门实验，在题目授权范围内辨认主体、目标资源和预期权限。
3. 对比正常请求与边界请求，记录变化的字段，并解释为什么它会影响授权判断。
4. 实际完成后再补充观察到的响应、原因分析和修复思路；没有验证的推测单独标注。

初学阶段值得反复追问的是：**服务端凭什么认定，这个身份可以对这个资源执行这次操作？**能把依据说清楚，才有助于把认证、授权和越权现象联系起来。
